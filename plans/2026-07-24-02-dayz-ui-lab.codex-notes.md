# Codex review — Phase 02 `dayz-ui-lab` and tooling boundary

## Veredicto

**[EXACT] El Intent de DPF C es correcto, pero el plan no está listo para
implementarse sin cinco enmiendas de contrato.** C1–C8 siguen siendo el alcance;
las enmiendas cierran observabilidad, determinismo y ownership sin ampliar el
producto.

Aliases de evidencia usados en esta revisión:

- `UI_RESEARCH`: proyecto local read-only `DayZ_UI_Research`;
- `LF_UILAB`: prototipo local read-only `LF_UILab`;
- `DAYZ_MCP`: proyecto local read-only `DayZ_MCP_dev`;
- `VANILLA`: snapshot de scripts DayZ fijado por el pack;
- `SKILL_SOURCE`: fuente activa de skills, no un destino editable.

## Hallazgos bloqueantes

### 1. C6 no dispone aún de geometría runtime por widget

**[EXACT]** El `DumpCurrentUILayout()` vanilla obtiene la raíz, recorre hijos y
siblings y solo imprime nombre, tipo y visibilidad
(`VANILLA/5_mission/mission/missionbase.c:357-418`). Una captura de pantalla más
ese dump no permite calcular los deltas por widget que exige
`product-spec.md:75`.

El engine sí expone el observable necesario: nombre, tipo, flags, sort, style,
visibilidad, color, alpha, posición/tamaño local y posición/tamaño de pantalla
(`VANILLA/1_core/proto/enwidgets.c:121-154`), además de parent, children y
sibling (`:158-173`). `UIScriptedMenu.GetLayoutRoot()` entrega la raíz del menú
(`VANILLA/3_game/tools/uiscriptedmenu.c:66-78`).

**[DESIGN] Enmienda requerida:** C6 debe exigir una sonda ingame first-party que
emita un snapshot estructurado y completo del árbol. El bundle de calibración
combinará ese snapshot con screenshot, RPT, build, resolución y escenario. El
RPT vanilla por sí solo no podrá cerrar C6.

### 2. C3 mezcla dos alcances de determinismo

**[EXACT]** El renderer actual solo genera HTML
(`UI_RESEARCH/renderer/build_viewer.py:205-217`) y declara que fuentes,
PAA/EDDS, mutaciones de script y auto-layout de spacers no están emulados
(`:13-15,96-97`). No existe todavía raster PNG ni diff visual.

**[EXACT]** Pedir «PNG byte-idéntico» sin fijar browser/rasterizador, fuentes,
codec, sistema y versiones no define un oráculo reproducible. También confunde
los bytes del contenedor PNG con los píxeles decodificados.

**[DESIGN] Enmienda requerida:**

1. `render.json` normalizado será byte-idéntico entre ejecuciones limpias y no
   contendrá timestamps ni paths privados.
2. Los píxeles RGBA decodificados y el PNG serán idénticos dentro de un perfil
   de raster fijado y registrado.
3. Fuera de ese perfil, el artefacto se marcará `non_canonical`; no se
   presentará como golden.
4. DayZDiag seguirá siendo la autoridad final de píxeles y comportamiento.

### 3. `LF_UILab` es prior art reutilizable, no una base lista

**[EXACT]** El prototipo ya aporta un `ScriptView`, carga de layout, manejo de
input/cursor, centrado y export a RPT
(`LF_UILAB/scripts/4_World/LF_UILab_MainView.c:7-88,206-325`;
`LF_UILAB/scripts/4_World/LF_UILab_TestRunner.c:293-326`).

**[EXACT]** No está completo: solo registra V00
(`LF_UILAB/scripts/4_World/LF_UILab_SelfTest.c:77-91`) y cuatro paneles siguen
marcados pendientes
(`LF_UILAB/gui/layouts/LF_UILab_Main.layout:371-490`). Además declara
`"DabsFramework"` en `requiredAddons[]`
(`LF_UILAB/config.cpp:7-11`), patrón E01 del checklist cuyo contrato correcto es
`DF_Scripts` o `DF_GUI`.

**[EXACT]** Su textura procedural
`#(argb,8,8,3)color(1,1,1,1,CO)` se carga antes de tintar
(`LF_UILAB/scripts/3_Game/LF_UILab_Config.c:13-15,78-84`); el mismo patrón ya
produjo `Bad texture name` en el Sorter V4
(`VAULT/AI/10_Projects/DayZ_UI_Research/research/2026-07-24-lfpg-sorter-v4-postmortem-codex.md:103-108`).

**[DESIGN] Enmienda requerida:** auditar y aprovechar conceptos/fixtures de
`LF_UILab`, pero crear una sonda mínima sin dependencia obligatoria de Dabs.
No se copiará el prototipo como implementación probada.

### 4. La captura MCP actual no es todavía un golden UI canónico

**[EXACT]** El backend puede restringir una captura por `cmdline_match` o
`client_pid` y escribir un PNG
(`DAYZ_MCP/tools/mcp_capture.py:313-372`). Sin embargo, la tool pública
`capture_screenshot` no expone ninguno de esos selectores
(`DAYZ_MCP/tools/dayz_mcp/server.py:1223-1251`), y su persistencia full-resolution
es JPEG
(`DAYZ_MCP/tools/mcp_capture.py:451-459,462-496`). En una futura prueba de dos
clientes, esto puede capturar la ventana equivocada o introducir compresión con
pérdida.

**[EXACT]** El lifecycle existente ya devuelve `run_id` y directorios de
artefactos por modo
(`DAYZ_MCP/tools/dayz_mcp/dayz_test_tool.py:316-340,451-516`) y exige el
`run_id` exacto para stop (`:519-571`). No debe aparecer una segunda autoridad
de procesos.

**[DESIGN] Enmienda requerida:** Fase 02 define e importa un
`engine-capture-v1` independiente del transporte. La automatización MCP se
implementará después de estabilizar ese schema, como delta estrecho y
run-bound dentro de Fase 05. El laboratorio debe poder cerrar sus gates con
import manual y DayZDiag, sin depender del bridge.

### 5. Pooling no pertenece al camino crítico de fidelidad

**[EXACT]** Task 6 mezcla calibración —necesaria para C6— con pooling
(`plans/2026-07-24-02-dayz-ui-lab.md:78-85`). Pooling es una optimización que no
mejora el oráculo visual y puede introducir estado fantasma, ownership
incorrecto o callbacks duplicados.

**[DESIGN] Enmienda requerida:** ejecutar el benchmark solo después de tener
parser, escenarios, raster, diff y calibración verdes. «No promover pooling»
será un resultado válido si el beneficio no es reproducible; C7 exige medir,
no adoptar.

## Corrección de doctrina de la skill

**[EXACT]** La skill activa ya registra que mezclar ejes exactos y
proporcionales es normal en vanilla
(`SKILL_SOURCE/dayz-ui-development/SKILL.md:155-172`), mientras su referencia
aún lo llama frágil y prescribe all-exact/all-proportional
(`SKILL_SOURCE/dayz-ui-development/references/plan-to-implementation.md:102-107`).
La reconciliación de Task 7 debe eliminar esa contradicción antes de promover
`dayz-ui`.

## Arquitectura propuesta

**[DESIGN] Un producto, dos planos de ejecución y una sola IR:**

1. **Core offline `dayz-ui-lab`:** parser → IR versionada → composición de
   escenarios → render spec → raster → diff → report.
2. **Visor interactivo:** consume exactamente la misma IR/render spec que el
   raster headless; no mantiene un segundo parser ni una segunda geometría.
3. **Sonda ingame source-only:** carga fixtures first-party, aplica el estado,
   espera la actualización de UI y exporta el árbol runtime mediante los
   getters verificados.
4. **Importador de captura:** convierte screenshot + snapshot + RPT + metadata
   en `engine-capture-v1` y cuantifica deltas por widget.
5. **Adaptador MCP opcional:** transporta y automatiza el mismo bundle; no posee
   semántica UI ni un lifecycle paralelo.

Artefactos previstos:

- `scenario.json`: estado declarativo y composición;
- `render.json`: salida semántica normalizada;
- `preview.html`: inspección interactiva;
- `preview.png`: raster del perfil fijado;
- `diff.json` y `report.html`: hallazgos accionables;
- `engine-capture-v1/manifest.json`, `screenshot.png`,
  `widget-tree.json` y RPT local/sanitizado.

Los RPT completos, capturas de terceros y paths físicos quedan fuera del
payload Git. Solo entran fixtures first-party o extractos depersonalizados.

## Fronteras de tooling

- **[DESIGN] Nuevo:** construir `dayz-ui-lab` y su sonda ingame como el tooling
  principal de Fase 02.
- **[DESIGN] MCP:** definir ahora el schema de integración; no cambiar
  lifecycle, bridge, watch mode ni captura pública hasta el plan de Fase 05.
  El único delta futuro justificable es captura lossless seleccionada por
  `run_id`/cliente y ligada al bundle.
- **[EXACT] py3d:** no tocar en Fase 02. El fork se declara MLOD
  (`tools/py3d/py3d/__init__.py:1-6`) y rechaza ODOL/no-MLOD
  (`tools/py3d/py3d/__main__.py:36-47`). Proxy/animación/export/ODOL ya tienen
  su workstream en `plans/2026-07-24-04-py3d-and-domain-skills.md:49-59`.
- **[DESIGN] Codecs de assets:** PAA/EDDS permanece módulo interno del lab en
  esta fase. Solo se extraerá a herramienta compartida cuando exista un segundo
  consumidor real y una licencia/procedencia cerrada.

## Viability gates requeridos antes de implementar

### VG-01 — Parser B19/B20

- Leaf válido sin bloque hijo: parsea con cero `missing-child-block`.
- Llave desbalanceada: error con línea/columna.
- Continuación física LF y CRLF: mismo valor lógico que el micro-fixture
  DayZDiag.
- Barra huérfana/escape inválido: fallo explícito.
- Corpus: LFPG + 319/319 público + 46/46 TraderX, exit 0.

### VG-02 — IR y escenarios

- Shell → subview → tres cards conserva identidad, orden y geometría a
  1920×1080 y 3440×1440.
- Path roto y ciclo fallan cerrados.
- La identidad de widget usa ancestry + sibling index + nombre/tipo; no depende
  solo de nombres potencialmente repetidos.

### VG-03 — Determinismo y assets

- Dos ejecuciones limpias producen el mismo `render.json`.
- Dos ejecuciones dentro del perfil fijado producen el mismo buffer RGBA y PNG.
- `.styles`, `.imageset` 9-slice y fuente first-party resuelven sin fallback.
- Asset ausente produce finding/fallo estable, no sustitución silenciosa.

### VG-04 — Diff accionable

- Fixture negativa produce exactamente reference-missing, clipping, overlap y
  estado ausente esperados.
- Control positivo produce cero hallazgos.
- Cada finding identifica escenario, widget estable, propiedad, esperado,
  observado y fuente editable.

### VG-05 — Captura y calibración engine

- Snapshot ingame cerrado por sentinels, sin registros truncados.
- Cada widget contiene tipo/identidad/visibilidad/style/color/alpha y geometría
  local + pantalla.
- Screenshot, snapshot, RPT y manifest coinciden en escenario, build,
  resolución y ejecución; cualquier mezcla falla cerrada.
- El informe calcula deltas geométricos por widget sin inventar un threshold
  global.

### VG-06 — MCP opcional

- Import manual y DayZDiag cierran C6 sin MCP.
- Cuando exista adapter, un `run_id` resuelve un único cliente y un PNG
  lossless; cliente ambiguo, run inexistente o artefacto incompleto falla
  cerrado.
- MCP no duplica start/stop ni ownership.

### VG-07 — Pooling

- Create/unlink y reuse producen el mismo snapshot/render.
- Reset/rebind/unlink/ownership/null handling no dejan estado ni callbacks
  fantasma.
- Solo se promueve con beneficio medido y reproducible; si no, se documenta
  «no adoptar».

## Secuencia propuesta

1. Enmendar DPF C3/C6 y el plan; cerrar la feature spec y estos gates.
2. Corregir parser B19/B20 y fijar la IR.
3. Implementar escenarios, composición y diff estructural.
4. Implementar visor + raster headless sobre la misma render spec.
5. Resolver assets first-party y determinismo del perfil.
6. Auditar/reducir `LF_UILab` a sonda first-party y calibrar con DayZDiag.
7. Ejecutar el experimento de pooling sin presuponer adopción.
8. Reconciliar skill/Obsidian, evals, gates y promoción.
9. Llevar la automatización run-bound de captura a Fase 05.

## Decisión aprobada

**[EXACT] El usuario aprobó conjuntamente el 2026-07-25:**

1. determinismo semántico cross-run + determinismo de píxeles en perfil fijado;
2. snapshot ingame estructurado como requisito de C6;
3. `dayz-ui-lab` nuevo con sonda first-party sin dependencia obligatoria de
   Dabs, usando `LF_UILab` solo como prior art;
4. schema MCP ahora y cambio MCP estrecho después.

La DPF y el plan de Fase 02 incorporan estas cuatro decisiones antes del primer
slice de implementación.
