# Fase 02 — `dayz-ui-lab`

> **Modo de ejecución:** Codex inline. El golden final pertenece a DayZDiag;
> el visor offline no se declara engine-faithful por sí solo.

## Objetivo y traza DPF

Cerrar C1–C8: convertir el renderer existente en un laboratorio de escenarios
que permita implementar, observar, comparar e iterar una UI antes del test
ingame.

## Task 1 — Research/viability gate

- [ ] Inventariar parser, resolver, viewer, tests y planes vivos del renderer.
- [ ] Fijar B19/B20 como defectos de parser, no como errores de los layouts.
- [ ] Verificar la semántica CRLF/LF de continuación con micro-fixture DayZDiag.
- [ ] Fijar builds/hashes de los corpora y sus licencias.
- [ ] Convertir los viability gates actuales en una feature spec cerrada.
- [ ] No escribir UI code hasta que C1 tenga fixtures positivas y negativas.

## Task 2 — Base honesta del parser

- [ ] Leaves válidos generan 0 `missing-child-block`.
- [ ] Llaves desbalanceadas siguen fallando con línea/columna.
- [ ] Continuaciones LF/CRLF producen el mismo valor lógico que DayZDiag.
- [ ] Barra huérfana y escape inválido fallan explícitamente.
- [ ] Gate: LFPG + 319/319 público + 46/46 TraderX, exit 0.

## Task 3 — Escenarios y composición

- [ ] Schema versionado con entrypoint, resolución, subviews, collections,
  bindings, visibility, color/alpha/posición, tabs, control state, modal y
  pointer.
- [ ] Componer shell→subview→N child layouts conservando identidad/orden.
- [ ] Detectar ciclo y path roto fail-closed.
- [ ] Generar estados nombrados, no un mapa global mutable.
- [ ] Gate: fixture first-party de tres cards en 1920×1080 y 3440×1440.

## Task 4 — Assets y render determinista

- [ ] Resolver `.styles`, `.imageset`, 9-slice, EDDS/PAA y TTF/FNT propios.
- [ ] Nunca copiar assets de los referentes.
- [ ] `ItemPreview`/`PlayerPreview` usan placeholder honesto o fixture con
  procedencia.
- [ ] Render JSON y PNG normalizados por escenario/resolución.
- [ ] Gate: dos renders iguales son byte-idénticos y no hay fallback silencioso.

## Task 5 — Diff e iteración del agente

- [ ] Diff estructural por widget/estado.
- [ ] Overlays de overflow, clipping, overlap y reference missing.
- [ ] Salida accionable que identifique qué editar y por qué.
- [ ] Ciclo documentado request→layout/scenario→render→diff→edit→rerender.
- [ ] Gate: Sorter V4 TEST produce solo los defectos conocidos; producción y
  fixtures positivas no heredan esos findings.

## Task 6 — Calibración DayZDiag y pooling

- [ ] Capturar escenarios curados en resoluciones/aspect ratios definidos.
- [ ] Conservar screenshot, snapshot, build y RPT.
- [ ] Cuantificar deltas por widget sin inventar un umbral pixel global.
- [ ] Benchmark create/unlink vs pool con mismo output/corpus.
- [ ] Promover pooling solo con reset/rebind/unlink/ownership/null handling
  completos y 0 estado/callback fantasma.

## Task 7 — Skill y cierre

- [ ] Skill `dayz-ui` posee el contrato completo de layouts/widgets/HUD/menús,
  delega parsing/render/diff al tool `dayz-ui-lab` y conserva DayZDiag como
  golden final.
- [ ] Añadir Forward Contract visual y árboles de diagnóstico.
- [ ] Evals cubren UI vacía, style ausente, colección no compuesta, tooltip,
  fuente y offline≠engine.
- [ ] Validator pack + eval harness + corpus + DayZDiag verdes.
- [ ] Reconciliar el legado `dayz-ui-development` sin dejar dos skills propias
  activas con triggers solapados.
- [ ] Actualizar la nota Obsidian conservando evidencia privada; promover
  `dayz-ui` desde el commit validado y verificar readback/recibo.
- [ ] Revisión fría Codex y actualización DPF/HANDOFF.

## Hard stops

- B19/B20 abiertos.
- Corpus externo sin commit/hash/licencia.
- Preview presentada como prueba del engine.
- Asset de tercero dentro del payload.
- Diff basado en output no determinista.
- Pool sin benchmark y lifecycle completo.
- `PROMOTION-UNROUTED`, `PROMOTION-DRIFT` o dos skills propias con triggers
  solapados.
